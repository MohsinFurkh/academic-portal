Part A · accounts

User accounts, the passwd file, groups

/etc/passwd — seven colon-separated fields

app:x:997:997:Application service account:/opt/app:/usr/sbin/nologin
 1  2  3   4              5                    6            7
  1. Username — what you type.
  2. Password placeholder — always x today, meaning "the real hash is in /etc/shadow". An empty second field means no password is required at all.
  3. UID — the number the kernel actually enforces. Names are a convenience for humans.
  4. GID — the primary group.
  5. GECOS — free-text comment (full name, contact).
  6. Home directory.
  7. Login shell — /usr/sbin/nologin for service accounts that must never log in.

/etc/passwd is world-readable — hence /etc/shadow (root-only, mode 0640) for hashes, plus ageing and lockout fields. /etc/group lists groups and their supplementary members.

Two facts that explain most confusion

1 · The kernel enforces UIDs, not names. Two names sharing UID 0 are both root. A file restored from a backup carries UIDs, so if UIDs differ between machines the ownership is silently wrong — the classic "the files came back owned by a stranger" incident, and the reason containers pin numeric UIDs.

2 · A user has one primary group and any number of supplementary groups. The primary group owns files you create; supplementary groups grant access.

id app                # uid, gid and all groups
groups app
getent passwd app     # works with LDAP/SSSD too, unlike grep
usermod -aG docker rita   # -a is MANDATORY: without it you
                          # REPLACE all supplementary groups

Group membership is read at login, so a user added to a group must log out and back in — newgrp or a fresh session. "I added them to the group and it still says permission denied" is nearly always this.

UID ranges: 0 = root; 1–999 system and service accounts; 1000+ humans (/etc/login.defs). Note that docker group membership is effectively root — a container can mount the host filesystem.

Part A · accounts

Creating user accounts

A human user

useradd -m -s /bin/bash -c "Rita Sharma" rita
passwd rita                       # set the initial password
passwd -e rita                    # force a change at first login
usermod -aG sudo,developers rita
chage -M 90 -W 7 rita             # password ageing policy

-m create the home directory and populate it from /etc/skel — omit it and the user logs in to a non-existent home, which breaks almost everything · -s login shell · -c GECOS comment. adduser on Debian is a friendlier interactive wrapper; useradd is the low-level tool and the one to use in scripts.

Bulk creation — the classic automation task

while IFS=, read -r user name grp; do
    id -u "$user" &>/dev/null && continue   # idempotent!
    useradd -m -s /bin/bash -c "$name" -G "$grp" "$user"
    echo "$user:$(openssl rand -base64 12)" | tee -a /root/newpw.txt | chpasswd
    passwd -e "$user"
done < students.csv
chmod 600 /root/newpw.txt

Note the id -u … && continue: the script is safe to re-run after it fails on row 180 of 300.

A service account — for your automation

useradd --system \
        --home-dir /var/lib/backupsvc \
        --create-home \
        --shell /usr/sbin/nologin \
        --comment "appdb backup job" \
        backupsvc
  • --system — a UID below 1000, no password ageing, not a human.
  • --shell /usr/sbin/nologin — nobody can log in as it, even with a stolen password. Interactive access is via sudo -u backupsvc, which is auditable.
  • No password at all — the account is locked by default and stays that way.
  • Its own home for state and credentials, mode 0700.

Removing accounts

usermod -L rita            # lock first — reversible
pkill -u rita              # end their sessions
userdel -r rita            # delete + home. IRREVERSIBLE.
find / -nouser -ls         # find orphaned files afterwards

Lock, wait, then delete. Deleting immediately destroys the home directory and leaves files elsewhere owned by a bare UID — which is then inherited by the next user created, who silently gains access to them.

Part B · permissions

Ownership and permissions

-rwxr-x---  1 app  deploy  512 Sep 1 03:00 run.sh
 │└┬┘└┬┘└┬┘    └┬┘  └──┬─┘
 │ │  │  │      │      └─ group
 │ │  │  │      └──────── owner
 │ │  │  └─ other:  ---   (0)
 │ │  └──── group:  r-x   (5)
 │ └─────── owner:  rwx   (7)
 └───────── type: - file  d dir  l symlink
BitOn a fileOn a directory
r (4)read contentslist the names inside
w (2)modify contentscreate, rename and delete entries inside
x (1)execute ittraverse it — enter, or access anything through it

The directory column is where students lose marks and engineers lose hours. Two consequences: ① r without x lets you list names but read nothing — every path through the directory is denied. ② w on a directory lets you delete a file you cannot even read, because deletion modifies the directory, not the file. Permission to remove a file has nothing to do with the file's own permissions.

Octal, umask, and the special bits

chmod 640 app.conf     # rw- r-- ---
chmod 750 run.sh       # rwx r-x ---
chmod u+x,go-w run.sh  # symbolic form
chmod -R u=rwX,go= dir # capital X: x only on dirs
chown app:deploy run.sh

umask 022  → new files 644, dirs 755   # default
umask 077  → new files 600, dirs 700   # for secrets

umask subtracts. Files are born 666 and directories 777, minus the mask. Set umask 077 at the top of any script that writes credentials or dumps, so the file is private from the instant it is created — a chmod afterwards leaves a window in which it was world-readable.

  • setuid (4000) — the program runs as its owner, not as you. That is -rwsr-xr-x on passwd. A setuid-root binary you wrote is a root exploit waiting to be found. Never set it on a shell script — most kernels ignore it precisely because it is unfixable.
  • setgid (2000) — on a directory, new files inherit the directory's group. Genuinely useful for shared team directories.
  • sticky (1000) — on a world-writable directory, only the owner may delete their own files. That is the t in /tmp's drwxrwxrwt.

Finer-grained rules than owner/group/other: setfacl -m u:jenkins:rx /opt/app. A + at the end of the mode string in ls -l means an ACL is present — and is easily missed when auditing.

Part C · least privilege

Designing the identity for an automated job — and slide 2 answered

The six problems on slide 2

  1. -rwxrwxrwx deploy.sh — world-writable and root-owned. Any user can rewrite it, and it then runs as root. This is a complete privilege escalation, and it is the worst line on the list. Should be 750.
  2. -rwsr-xr-x helper — setuid root, world-executable. Every user runs it as root; one flaw in it is a root shell for anyone.
  3. drwxrwxrwt spool/ — world-writable is at least sticky, so users cannot delete each other's files. Acceptable for /tmp; a smell inside an application directory.
  4. db.password at 0600 root — correct. Note that correct here also means the service reading it must run as root, which pushes you towards a dedicated account plus a group-readable secret instead.
  5. NOPASSWD: systemctl restart myapp — reasonable, narrowly scoped.
  6. NOPASSWD: /usr/bin/vi /etc/myapp/config — this is full root. From inside vi, :!/bin/bash spawns a root shell, and :w /etc/shadow writes anywhere. Any sudo rule granting an editor, a pager, find, tar, awk or an interpreter grants everything — they all have a shell-escape. Use sudoedit, which edits a copy as you and installs it as root.

The design, done properly

  1. One service account per job, --system, nologin. Never run automation as root "because it is simpler", and never as a person's account.
  2. Grant access with groups, not by loosening permissions. Put backupsvc in a dbdump group and make the credentials file 0640 root:dbdump.
  3. The script is not writable by the account that runs it. 0750 root:backupsvc — read and execute, never modify. This single rule blocks problem 1 above.
  4. Narrow sudo rules, full paths, no wildcards, no interpreters or editors. Check them with sudo -l -U svc and remember every rule you write will be probed.
  5. Secrets: 0600, owned by the account, umask 077 in the script, never in Git, never on a command line.
  6. SSH keys, not passwords, for anything remote — and restrict them with command="…",no-port-forwarding in authorized_keys so a stolen key can run only the one job.
# audit your own host
find / -xdev -perm -0002 -type f -ls   # world-writable files
find / -xdev -perm -4000 -ls           # setuid binaries
find / -xdev -nouser -o -nogroup       # orphaned files
Part D · bash

Working with bash: the start-up files

Shell kindExampleReads
Loginconsole login, ssh host, su -/etc/profile, then the first of ~/.bash_profile, ~/.bash_login, ~/.profile
Interactive non-logina new terminal tab/etc/bash.bashrc, ~/.bashrc
Non-interactiveyour script, your cron job, ssh host cmdNothing. Only $BASH_ENV if set.

Row three is the whole point. It is the formal statement of the cron problem from Lecture 6: your script inherits no aliases, no functions, no PATH additions, no virtualenv, no JAVA_HOME. Everything it needs, it must declare.

Why most ~/.bash_profile files source ~/.bashrc: otherwise a login shell would not see your interactive settings at all — the sourcing is a convention papering over the table above.

# Test whether a shell is interactive
[[ $- == *i* ]] && echo interactive
# Guard prompts in scripts: refuse to ask when nobody can answer
[[ -t 0 ]] || { echo "no tty; use --yes" >&2; exit 2; }

Variables, environment and export

name="value"          # shell variable: this shell only
export NAME="value"   # environment: inherited by children
unset NAME

source ./config.sh     # run IN this shell (changes persist)
./config.sh            # run in a CHILD (changes are lost)

A child process cannot change its parent's environment. That is why cd must be a builtin, why source exists, and why "the script sets the variable but it is gone afterwards" is not a bug.

Do not put secrets in the environment. On many systems /proc/PID/environ is readable by the owner, children inherit them by default, and crash handlers love to dump the whole environment into a bug report.

Useful ones you did not set: $? last exit status · $$ this PID · $! last background PID · $# argument count · $@ all arguments · $0 script name · $- current shell options · $IFS the word-splitting characters.

Part D · bash

Shell features — the expansion order is the lecture

Bash expands a line in this fixed order: brace → tilde → parameter → command substitution → arithmetic → word splitting → pathname (globbing) → quote removal. Word splitting and globbing happen after your variable is substituted — which is exactly why an unquoted $file containing a space becomes two arguments, and why one containing * turns into a list of filenames. Every quoting bug in this course is a consequence of that one sentence.

Expansion

{a,b}.txt      → a.txt b.txt
{1..5}         → 1 2 3 4 5
~rita          → /home/rita
$HOME          → /home/rita
$(date +%F)    → 2026-09-03
$(( 3 * 7 ))   → 21
*.log          → all matching files
?              → any one character
[abc]          → one of a, b, c

shopt -s nullglob   # unmatched glob → nothing,
                    # not the literal pattern
shopt -s globstar   # ** recurses

Redirection and pipes

cmd > out        # stdout, truncate
cmd >> out       # stdout, append
cmd 2> err       # stderr
cmd &> both      # both (bash)
cmd > f 2>&1     # both — ORDER MATTERS
cmd 2>&1 > f     # WRONG: stderr to the
                 # old stdout, i.e. the tty
cmd < in         # stdin from a file
a | b            # stdout of a → stdin of b
a |& b           # both streams into b
cmd <<< "text"  # here-string
cmd <<'EOF' … EOF  # here-doc (quoted
                 # EOF = no expansion)

Control and inspection

a && b      # b only if a succeeded
a || b      # b only if a failed
a ; b       # b regardless
cmd &       # background
jobs; fg; bg; wait
nohup cmd & # survive logout

type -a ls   # alias? builtin? file?
command -v jq   # is it available?
help read   # builtins have no man page
set -x       # trace what actually runs

Builtins beat externals in loops. [[ ]], printf and parameter expansion run inside the shell; [, expr and basename fork a process each time. Over 100,000 iterations that is the difference between one second and two minutes.

Terminals open · 8 minutes

Give your Unit 2 script a proper identity

Do it on a VM or container you can break 8:00

Tasks

  1. Create a --system, nologin account for your job, with its own home.
  2. Install the script as 0750 root:<svc> in /usr/local/bin. Confirm the service account can execute it and cannot modify it.
  3. Create /etc/<job>/config as 0640 root:<svc> and a secret as 0600 owned by the service account.
  4. Create /var/log/<job>/ and /var/lib/<job>/ owned by the account, mode 0750.
  5. Run it: sudo -u <svc> /usr/local/bin/<job>.sh. Fix every permission error by adjusting ownership or groups — not by chmod 777.
  6. Add umask 077 at the top and verify every file it creates is 0600.

Then prove these three claims

  1. Directory w beats file permissions. As user A, create -r--r--r-- file owned by A in a directory user B can write. Have B delete it. It works. Why?
  2. r without x on a directory is useless. chmod 644 a directory, then try to cat a file inside it whose name you already know.
  3. Non-interactive shells read nothing. Put alias hi='echo hello' in ~/.bashrc, verify it works in your terminal, then call it from a script and from cron. Explain both results.

Each of these is a two-minute experiment that permanently fixes a misconception. Do them once and you will never guess at these again.

Unit 4 closes with six rules

  1. Every job runs as a dedicated, non-login service account — never root, never a person.
  2. The script is not writable by the account that runs it.
  3. Grant access with groups, never by widening permissions.
  4. Secrets are 0600, created under umask 077, never in Git, never on a command line, never in the environment.
  5. Sudo rules are narrow and contain no interpreter — an editor in a sudo rule is root access.
  6. Non-interactive shells read no start-up files. Declare what you need.
