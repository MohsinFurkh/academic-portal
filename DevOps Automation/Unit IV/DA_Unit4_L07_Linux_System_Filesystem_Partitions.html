Part A · the system

The Linux system: three layers you keep confusing

1 · The kernel

Linux, strictly, is only this. It owns the hardware and provides processes, memory, the filesystem layer, networking and device drivers. Programs reach it through system calls — open, read, write, fork, execve.

Everything you type is ultimately a sequence of system calls. strace -f ./script.sh shows you exactly which — the best debugging tool nobody teaches.

2 · The userland

The C library (glibc, musl) plus the standard utilities — GNU coreutils, findutils, grep, sed, awk — plus service managers and package tools. This is what you actually call.

Portability warning: GNU and BusyBox versions of the "same" command differ. sed -i takes no argument on GNU and requires one on BSD/mac; date -d is GNU-only. Scripts written on Ubuntu break inside Alpine containers for exactly this reason.

3 · The shell

A program like any other, whose job is to read your line, expand it, and ask the kernel to run the result. It is your primary interface to the other two layers, and it is what runs every script in this course.

A distribution = kernel + userland + package manager + init + policy. Debian, RHEL and Alpine differ in package names, paths and defaults far more than students expect — which is why "it worked on my machine" is a statement about the distribution, not about Linux.

Why this matters for automation. Your script is a userland program asking the kernel for things, through a shell that rewrites your text first. Nearly every mysterious scripting bug is one of three things: the shell expanded something you did not expect (Unit 5), the userland tool is a different implementation from the one you tested with, or the kernel refused because of permissions (next lecture).

Part B · the file system

The file system — and the answer to slide 2

Two organising ideas

1 · One tree. There are no drive letters. Every device, every partition, every network share is grafted onto the single tree rooted at / at a mount point. /home may be a different disk from / and paths look identical.

2 · Everything is a file. Regular files, directories, devices (/dev/sda), pipes, sockets, and kernel data (/proc, /sys) all answer to open/read/write. This is why a script can read the CPU count from /proc/cpuinfo with cat.

The inode — the actual file

A file's data and metadata live in an inode. A directory entry is just a name pointing at an inode. So a file is not its name — a name is a reference to a file. Three consequences follow, and they explain a great deal:

The three consequences

  • A file can have several names (hard links) and is destroyed only when the last one is removed. rm is really unlink.
  • Renaming a file does not disturb a process that has it open — the process holds the inode. This is Lecture 3's log-rotation problem.
  • Deleting a file that a process still holds open frees no space at all. The name is gone, so du cannot see it; the inode lives on until the process closes it, so df still counts it.

That is slide 2. Someone deleted /var/log/app.log to free space while the Java process had it open. 16 GB is still allocated, invisible to du, and still growing.

# find it
lsof +L1                 # NLINK 0 = deleted but open

# fix without a restart
: > /proc/4127/fd/3      # truncate through the fd

# or restart the process to release it
systemctl restart app

The lesson: never free space by deleting an open log. Truncate it (: > file) or rotate it properly and signal the daemon.

Hard vs symbolic links. A hard link is another name for the same inode — same filesystem only, no directories, indistinguishable from the "original". A symlink is a small file containing a path; it can cross filesystems and point at nothing (a dangling link). In scripts this distinction matters: -e follows symlinks and -L tests for them, realpath resolves them, and rm on a symlink to a directory removes the link, while rm -r symlink/ — with the trailing slash — goes through it and deletes the contents.

Part C · partitions

Partitions and mounting

$ lsblk
NAME   MAJ:MIN RM  SIZE RO TYPE MOUNTPOINTS
vda    253:0    0  100G  0 disk
├─vda1 253:1    0   20G  0 part /
├─vda2 253:2    0    8G  0 part [SWAP]
└─vda3 253:3    0   72G  0 part /var
vdb    253:16   0  500G  0 disk
└─vdb1 253:17   0  500G  0 part /var/lib/mysql

$ df -hT           # -T shows the filesystem type
$ df -i            # inode usage — the other way to run out
$ mount | column -t
$ findmnt /var     # which device backs this path?
$ blkid            # UUIDs — use these, not /dev names

Why separate partitions at all?

  • Blast radius. Runaway logs fill /var and stop there instead of wedging the whole system. A full / means you cannot even log in to fix it.
  • Different policies — mount /tmp with noexec,nosuid,nodev; mount data volumes noatime for speed.
  • Different hardware — fast SSD for the database, cheap bulk storage for archives.
  • Independent resize and snapshot, especially with LVM.

/etc/fstab — and the mistake that bricks a server

# device            mount        type  options              d p
UUID=6f2a-…         /            ext4  defaults             0 1
UUID=91bc-…         /var         ext4  defaults,noatime     0 2
UUID=c7d3-…         /var/lib/mysql xfs defaults,noatime     0 2
tmpfs               /tmp         tmpfs defaults,noexec,nosuid 0 0
  • Use UUIDs or labels, never /dev/sdb1. Device names are assigned in detection order and can change between boots — after which /var is mounted on the wrong disk.
  • A typo here does not fail at edit time; it fails at boot, and drops the machine into emergency mode with no network. Always run mount -a after editing, while you can still fix it. On a remote server this is the difference between a correction and a support ticket to the datacentre.
  • Consider nofail for non-essential volumes so a missing disk does not block boot.

For automation: a script that writes to /data must confirm /data is mounted, not merely that the directory exists. If the mount failed, the directory is still there — empty, on the root filesystem — and your backups quietly fill / instead. Check with mountpoint -q /data || exit 1.

Part D · directories

Common system directories (the FHS)

Programs

  • /bin, /sbin — essential commands; s = system/admin. On modern systems these are symlinks into /usr.
  • /usr/bin, /usr/sbin — the bulk of distribution-installed software. Package manager territory: never write here yourself.
  • /usr/local/bin — software you install by hand. This is where your automation scripts belong.
  • /opt — large self-contained third-party applications in their own directory.
  • /lib, /usr/lib — shared libraries and kernel modules.

Data and state

  • /etc — all system configuration, text files, no binaries. Back this up.
  • /var — data that changes: /var/log (logs), /var/lib (application state such as databases), /var/spool (queues, and crontabs), /var/cache, /var/backups.
  • /home — user home directories. /root — root's home, deliberately on / so it works when other mounts fail.
  • /tmp — world-writable scratch, cleared on reboot, often noexec. /var/tmp — scratch that survives reboot. /run — runtime state (PIDs, sockets), in memory, cleared every boot.
  • /srv — data served by this machine (web roots, ftp).

Virtual — not on any disk

  • /proc — kernel and process information as files. /proc/cpuinfo, /proc/meminfo, /proc/loadavg, /proc/<pid>/. Your system-information script is mostly reading this.
  • /sys — device and driver attributes, many of them writable.
  • /dev — device nodes. /dev/null discards, /dev/zero yields zeros, /dev/urandom yields randomness.
  • /boot — kernel and bootloader. Small, and famous for filling up with old kernels.

Sizes in /proc are reported as 0. Do not be alarmed — the content is generated when you read it.

Where your automation goes. Script → /usr/local/bin/backup.sh (or /opt/myapp/bin/). Its configuration → /etc/myapp/backup.conf. Its schedule → /etc/cron.d/myapp-backup. Its log → /var/log/myapp/backup.log. Its state (lock files, last-success markers) → /var/lib/myapp/ for persistent, /run/myapp/ for boot-scoped. Its temporary files → mktemp -d, cleaned by a trap. Follow this and any Linux administrator can operate your script without reading it.

Part D · directories

Where the shell fits — a preview of the next lecture

What happens when you press Enter

  1. Read the line and split it into words.
  2. Expand it: aliases, braces, ~, variables, command substitution, arithmetic, word splitting, then globbing. This is the step that surprises people, and Unit 5 is largely about it.
  3. Redirect — set up the file descriptors.
  4. Execute — is it a builtin, a function, or a program on PATH? If a program: fork, then execve.
  5. Wait and collect the exit status into $?.

The consequence for you: the command that runs is not the text you typed — it is the text after step 2. When a script misbehaves, run set -x and read what was actually executed.

Which shell is running your script?

Not necessarily the one you use interactively. On Debian and Ubuntu /bin/sh is dash, not bash — it is faster and strictly POSIX, and it does not understand [[ ]], arrays, local -n or <<<.

$ ls -l /bin/sh
lrwxrwxrwx 1 root root 4 … /bin/sh -> dash

$ echo $0            # the current shell
$ readlink -f /proc/$$/exe

So: cron runs /bin/sh, which is dash, which does not speak bash. That is one of the seven defects from Lecture 6, seen from the other side. Fix it in two places — a correct shebang in the script, and SHELL=/bin/bash in the crontab.

A login shell reads /etc/profile and ~/.bash_profile; an interactive non-login shell reads ~/.bashrc; a non-interactive shell — your script, your cron job — reads neither. Next lecture covers this properly.

Terminals open · 8 minutes

Answer these about the machine in front of you

Work down the list · write the command AND the answer 8:00

Investigate

  1. How many partitions, and which is mounted where? Is /var separate from /?
  2. Which filesystem type backs your home directory, and how full is it — by space and by inodes?
  3. Is /bin/sh bash or dash on this machine?
  4. How many CPUs does /proc/cpuinfo report? Get the same number two other ways.
  5. Find any deleted-but-open files: sudo lsof +L1. Anything holding space?
  6. Which device backs /tmp? Is it tmpfs? What does that imply for a script that leaves a large file there?

Then reproduce the slide-2 incident

# terminal 1 — a process holding an open file
cd /tmp
while :; do echo "line $(date)"; sleep 1; done > big.log &

# terminal 2
ls -l /tmp/big.log
rm /tmp/big.log            # the name is gone...
du -sh /tmp                # ...and du can no longer see it
lsof +L1 | grep big.log    # ...but there it is, NLINK 0
ls -l /proc/$(pgrep -f 'while :' | head -1)/fd/

Watch the file keep growing after you deleted it. When you have seen this once, you will never again "free up space" by deleting an active log — and you will diagnose that incident in two minutes instead of two hours. Kill the loop when done.

Five things to carry into every script you write

  1. A file is an inode, not a name. Renaming does not redirect an open process; deleting does not free space.
  2. A path is not a disk. Check mountpoint -q before writing where you expect a volume.
  3. Full has two meanings — bytes and inodes. Check both.
  4. Put things where the FHS says: /usr/local/bin, /etc, /var/log, /var/lib.
  5. /bin/sh is not bash, and your userland may not be GNU. Declare what you need rather than inheriting it.
