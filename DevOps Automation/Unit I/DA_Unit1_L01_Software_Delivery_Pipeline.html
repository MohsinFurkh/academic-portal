Prompts, in case your project was small

  • Who decided the code was good enough?
  • How was it compiled or packaged — and on whose machine?
  • Which tests ran? Who ran them? What if they had failed?
  • How did the files get onto the server? WinSCP? Git pull? A zip on WhatsApp?
  • Who restarted the service? How did you know it came back up?
  • If it had broken, how would you have got the old version back?

Count two numbers

H = number of steps a human performs.
T = total number of steps.

Keep H / T on your page. We will come back to it at the end of the hour.

In most student projects H/T is between 0.8 and 1.0 — that is, almost every step is a person. In a mature engineering organisation it is close to 0. The whole subject you are about to study is the process of driving that ratio down.

Reveal · what your H/T number costs

Manual delivery does not fail because people are careless

It fails because it is varied

  • Nobody performs a 40-step checklist identically twice. Not you, not a senior engineer, not at 3 a.m. on a Friday.
  • The steps live in someone's head, or in a Word document last updated two releases ago. That person is on leave.
  • Rare things go wrong most. A step performed once a month is a step nobody is good at.
  • Fear becomes the schedule. Because releasing is painful, you release rarely; because you release rarely, each release is huge; because each release is huge, it is more likely to break. This loop is the single most expensive thing in software delivery.

Automation attacks variance, not effort

Students usually think automation is about saving time. Saving time is a side effect. The real product is repeatability: the same inputs produce the same outputs, on any machine, at any hour, run by anyone.

  • A script that takes 30 minutes but is identical every time beats a 5-minute manual process that is slightly different every time.
  • An automated process is executable documentation. It cannot go stale — if it were wrong, it would fail.
  • It is auditable: version-controlled, reviewed, logged.

If it hurts, do it more often — and bring the pain forward.

Part A · the pipeline

The software delivery pipeline

An automated implementation of the path your software takes from version control to the user. Every change enters at the left; only changes that survive every stage reach the right.

Commitcompile, unit tests, static analysis
→
Buildone versioned artifact
→
Testintegration, acceptance
→
Stageproduction-like environment
→
Releasea human decision
→
Operatemonitor, roll back

Three rules that define it

  • Build the artifact once. The binary that ran the tests is the binary that reaches production. Never rebuild per environment.
  • Same process everywhere. Deploying to your laptop, to staging and to production uses the same script, with different configuration.
  • Fail fast, fail cheap. The cheapest, fastest checks run first.

Why the order is that order

A unit test costs milliseconds; an acceptance test costs minutes; a production incident costs a weekend. Stages are arranged so that a defect is caught by the cheapest stage capable of catching it. Each stage is a gate: it either passes the candidate on, or stops it and tells you why.

Note the one red box

Release stays a human decision in continuous delivery. The pipeline makes every change releasable; a person (or a business rule) decides whether to release it. Remove that person and you have continuous deployment — slide 10.

Part A · the pipeline

What "fully automated software delivery" means

It means

  • Every step is expressed as code — build scripts, test suites, deployment scripts, infrastructure definitions — and all of it is in version control alongside the application.
  • The pipeline is triggered by the commit, not by a person remembering.
  • Any team member can deploy any successful build to any environment, without specialist knowledge.
  • Rolling back is as automated as rolling forward. An un-undoable deployment is not finished work.
  • The state of every environment is known — which version, deployed when, by which pipeline run.

It does not mean

  • No humans. Humans review code, approve releases and decide priorities. Automation takes the mechanical work, not the judgement.
  • No testing effort. It moves testing earlier and makes it repeatable.
  • Buying a tool. Jenkins does not give you a pipeline any more than buying a stove gives you dinner.

The honest test of a pipeline. Delete every one of your environments except version control and the empty machines. Can you get the system running again by pushing a button? If yes, it is automated. If the answer contains the word "then someone", it is not — that "someone" is a single point of failure, and it is usually you.

Part B · build

The build process, and what makes a build automated

The build process — what actually happens

  1. Fetch the exact source revision from version control.
  2. Resolve dependencies at pinned versions (Maven, npm, pip, apt).
  3. Compile / transpile the source.
  4. Run unit tests and static analysis — a build that compiles but fails its tests is a failed build.
  5. Package into a single deployable artifact: .jar, .whl, .deb, a container image, a tarball.
  6. Stamp a version and publish it to an artifact repository.

Steps 1–6 are one command. If your build needs a person to "just also copy the config file", step 6 has not happened yet.

Properties of a good automated build

  • Single command. make, mvn package, ./build.sh.
  • Reproducible. Same revision in ⇒ same artifact out. Pinned dependency versions, no "latest", no machine-specific paths.
  • Clean-room. Runs on a fresh machine or container with nothing pre-installed but the declared toolchain — this is what catches "works on my machine".
  • Fast. Aim for under ten minutes to first feedback; developers stop waiting after that and start context-switching.
  • Self-diagnosing. When it fails, the log says which step and why, without anyone re-running it locally.
  • Versioned artifact. The output is traceable back to a commit hash.
# A build is a script in the repository — not a wiki page.
$ ./build.sh
--> resolving dependencies (locked)      ok   4.1s
--> compiling                            ok  12.7s
--> unit tests            214 passed     ok  31.2s
--> static analysis       0 blockers     ok   6.8s
--> package  dist/payments-1.8.3+9f2c1ab.tar.gz  ok
Part B · build

Automated test: the pipeline's immune system

Layers, cheapest first

LayerAsksCostHow many
UnitIs this function correct in isolation?msThousands
IntegrationDo these components talk correctly? Does the query run against a real database?secondsHundreds
AcceptanceDoes the system do what the user asked for?minutesTens
Non-functionalIs it fast enough, secure enough, available enough under load?minutes–hoursA few
Smoke / post-deployDid the thing we just deployed actually come up?secondsA handful

The three failures that kill test automation

  • Flaky tests. A test that fails randomly trains the team to ignore red builds. One flaky test is worse than no test — quarantine or delete it the day it appears.
  • Inverted pyramid. Mostly slow end-to-end UI tests, few unit tests: a two-hour suite nobody runs before pushing.
  • Tests that never fail. If a suite has never caught a bug, it is measuring nothing. Sabotage a line of code deliberately and confirm something goes red.

The rule: a red pipeline is the highest-priority item on the team. Not "I will look at it after lunch."

Part B · build

Automated deployment

Taking a built, tested artifact and making it the running system in a target environment — configured, started, verified — without manual steps.

What a deployment script does

  1. Fetch the exact artifact version (never rebuild).
  2. Apply environment configuration from outside the artifact.
  3. Run database migrations, forward-compatible.
  4. Stop / start or swap the service.
  5. Verify with a health check before declaring success.
  6. Register the version, and keep the previous one ready.

The two properties that matter

Idempotent — running it twice leaves the system in the same state as running it once. The script says "ensure the service is at version 1.8.3", not "install version 1.8.3". This is why a half-failed run can simply be re-run.

Reversible — you can get back to the previous version by the same mechanism, in minutes, without heroics. Blue-green and canary deployments are just structured ways of buying that reversibility.

Configuration is not code, but it is versioned

The same artifact must run in dev, staging and production. So hostnames, credentials and feature flags come from environment variables or a config service — never from an if (env == "prod") inside the code, and never from a file someone edits on the server. Secrets go in a secret store, not in Git.

Unit 5 is where you will actually write scripts with these properties.

Part C · the words people confuse

Three terms, three different commitments

Continuous Integration

Every developer merges to the mainline at least daily, and every merge triggers an automated build and test.

The commitment: no long-lived branches, and a broken build is fixed immediately. CI is a practice, not a server. Running Jenkins while everyone works on a three-week branch is not CI.

Continuous Delivery

Every build that passes the pipeline is deployable to production at any moment, by pressing a button.

The commitment: the software is always in a releasable state. Release becomes a business decision rather than a technical event.

Continuous Deployment

Every build that passes the pipeline goes to production automatically — no button.

The commitment: strong automated tests, feature flags, canary releases and fast rollback. Appropriate for a web service; not for a pacemaker, a satellite or a banking core.

All three depend on the same foundation: everything in version control, an automated build, an automated test suite you trust, and an automated deployment. That foundation is exactly the content of this course. The rest of the units teach you to build the pieces on Linux — scenarios (Unit 2), scheduling (Unit 3), the environment (Unit 4), and the scripts themselves (Unit 5).
