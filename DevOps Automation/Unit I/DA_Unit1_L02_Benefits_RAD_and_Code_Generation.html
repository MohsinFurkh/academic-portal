Do first · 5 minutes

Your manager says: "We ship fine by hand. Why should I pay for three weeks of pipeline work?"

1 · Alone, 2 min — write your three strongest arguments 2 · Pairs, 2 min — attack each other's arguments 3 · Class, 1 min 5:00

The rule for this exercise

An argument only counts if it is measurable. "It's best practice", "it's modern", "everyone does it" score zero. Your manager is not being unreasonable — they are being asked to spend money and they want a number.

Attack list — use these on your partner

  • "We only release once a month, so the saving is tiny."
  • "Our releases hardly ever fail."
  • "We'd spend three weeks building it and then the project ends."
  • "Ravi knows the deployment perfectly. Why replace him with a script?"

The last one is the interesting one. Hold your answer — slide 4 gives you a much better response than the one you are about to give.

Part A · benefits

Benefits of automated deployment

Direct benefits

  • Repeatability. The same steps every time, on every environment. The first and the one all the others rest on.
  • Speed. Lead time from commit to production falls from weeks to minutes.
  • Lower risk per release. Smaller, more frequent changes are easier to diagnose — when a release contains one change, you know which change broke it.
  • Fast recovery. Automated rollback turns an outage from hours into minutes.
  • Freed people. Engineers stop being deployment technicians.
  • Auditability. Every deployment is a logged, versioned, attributable event — which is what an ISO or SOC audit actually asks for.
  • Environment parity. The same script builds dev, staging and production, so "works in staging" starts to mean something.
  • Knowledge is in the repository, not in one person's memory.

The measurable version — the four delivery metrics

From the DORA research programme (Forsgren, Humble & Kim). These are the numbers to give your manager.

MetricQuestion
Deployment frequencyHow often do we successfully release?
Lead time for changeCommit → running in production: how long?
Change failure rateWhat fraction of releases cause a problem?
Time to restore serviceWhen it breaks, how fast are we back?

The counter-intuitive finding: speed and stability are not a trade-off. Teams that deploy more often also fail less often and recover faster, because their changes are small and their recovery path is practised.

Measure your four numbers before you automate. Without a baseline you cannot show the improvement, and the work looks like a cost.

Part B · adoption

Why automated deployment is the hinge of DevOps adoption

DevOps is usually described as culture — shared ownership between development and operations. True, but incomplete: you cannot share ownership of a process only one person can perform.

  • It removes the hand-off. A manual deployment forces a wall: developers "throw code over" and operations catch it. An automated deployment is a shared artifact both teams read, review and change.
  • It makes "you build it, you run it" possible. Developers can only be on call for what they can deploy and roll back themselves.
  • It converts arguments into evidence. "Your code broke it" / "your server broke it" becomes a pipeline run with logs.
  • It makes small batches affordable, which is what actually reduces risk.
  • It de-risks the expert. Ravi still knows the most — but now his knowledge is in a reviewed repository instead of dying with his notice period. This is the answer to the fourth attack on slide 2: you are not replacing Ravi, you are backing him up.

A realistic adoption path

  1. Everything into version control — including scripts, configuration and schema.
  2. Automate the build; make it one command.
  3. Automate the tests and make a red build the team's top priority.
  4. Automate deployment to a test environment — the first place it is safe to be wrong.
  5. Use the same script for production, with different configuration.
  6. Automate provisioning of the environment itself (infrastructure as code).
  7. Automate monitoring and rollback.

Where adoptions fail: starting at step 6 because it is the interesting one; buying tools before agreeing practices; and automating a broken process faithfully — automation amplifies whatever process it is given, including a bad one.

Part C · RAD

Rapid Application Development — overview

A development approach (James Martin, 1991) that replaces long up-front specification with rapid prototyping and continuous user feedback, under a fixed time budget.

The problem it was invented to solve

The waterfall model assumes requirements can be known completely before construction begins. For business software this is usually false: users cannot describe what they want in the abstract, but they can react decisively to something in front of them. By the time an 18-month waterfall project delivered, the requirements had moved.

RAD's bet: a working prototype elicits better requirements in one afternoon than a specification document does in a month.

Why RAD sits in an automation course

RAD is only possible if the mechanical cost of producing and delivering a build is near zero. Its two enabling technologies are exactly this course's subject:

  • Code generation and reusable components — so a prototype takes days, not months.
  • Automated build and deployment — so the user sees each iteration immediately.

Attempt RAD with a manual, week-long release process and you get the worst of both worlds: no specification and no feedback. RAD without automation is just an undocumented project.

Agile, Scrum and XP later generalised these ideas; modern CI/CD is the machinery RAD needed and did not have.

Part C · RAD

The four phases

1 · Requirements planningscope, not specification
→
2 · User designprototype ⇄ feedback, repeatedly
→
3 · Constructionharden the accepted prototype
→
4 · Cutovermigrate, train, go live

1 · Requirements planning

Users, managers and developers agree the business problem, scope and constraints — days, not months. The output is a bounded problem, not a signed-off specification.

2 · User design

The heart of RAD, and a loop, not a step. Build a prototype, show it to real users, watch them use it, revise. Repeat until the design is accepted. Models and prototypes evolve together.

3 · Construction

Turn the accepted prototype into a production system: error handling, security, performance, tests. Users stay involved and can still request changes. Much code is generated or assembled from components.

4 · Cutover

Data migration, user training, acceptance testing, changeover to live running. The phase teams under-plan — and the one where automated, rehearsed deployment pays for itself outright.

The classic RAD failure: the prototype from phase 2 is shipped as the product, skipping phase 3. It demos beautifully, has no error handling, no tests and no security, and becomes a system nobody can maintain. A prototype is an instrument for learning, not a deliverable — decide before you start whether you will keep it or throw it away, and say so out loud.

Part C · RAD

Essential aspects — and when RAD is the wrong choice

What RAD requires to work

  • Genuine user involvement. Not a monthly review — a user in the room who can decide. Without this, RAD collapses immediately.
  • Small, skilled, empowered teams (often 4–8) that can decide without escalation.
  • Timeboxing. The deadline is fixed and scope flexes to fit it — never the reverse. This is the discipline that stops "rapid" becoming "endless".
  • Iterative prototyping with short cycles measured in days.
  • Reuse and automated tooling — component libraries, frameworks, code generators, scaffolding, automated build and deployment.
  • Active management of scope creep, which prototypes invite: every demo produces ten new ideas.

When not to use RAD

  • Safety- or life-critical systems. Avionics, medical devices, nuclear control: these need formal specification and verification, not iteration on users.
  • Very large systems that cannot be decomposed into independently demonstrable pieces.
  • High technical risk — novel algorithms, hard performance targets — where the difficulty is not in the requirements at all.
  • No user availability, or requirements fixed by regulation or contract.
  • Teams without senior engineers. RAD trades documentation for skill; if the skill is absent, the trade is a loss.

RAD reduces requirements risk. It does nothing for technical risk — and it increases documentation risk.

Part D · code generation

Code generation: writing programs that write programs

A generator takes a higher-level specification — a schema, a model, an interface definition, a template — and mechanically produces source code from it.

Why it belongs to automation

  • It removes a class of human error entirely. Hand-written boilerplate is where typos live; generated boilerplate is uniformly right or uniformly wrong, and uniformly wrong is fixable in one place.
  • It enforces consistency. Every generated data-access class follows the same pattern, so a reviewer reads one and understands all.
  • The specification becomes the source of truth. Change the schema, regenerate, and every consumer follows — instead of hunting for the places that need editing.
  • It makes RAD's timescales possible. A prototype with CRUD screens over 20 tables is an afternoon, not a month.

The two rules

1 · Never edit generated code. The next regeneration destroys your edit. Extend it instead — inheritance, partial classes, a separate hand-written file — and keep generated output in clearly named directories.

2 · Generate from a versioned specification, and regenerate in the build. If the generator is run once by hand on somebody's laptop, the output is now hand-written code with an unusual history.

Costs to weigh honestly: debugging through generated code is harder, a generator is another dependency to maintain, and generated code can be verbose. Use one when the pattern is repetitive, mechanical and stable — not for the interesting 10% of your system.

Part D · code generation

Categories of code generators

The primary split — passive vs active. A passive generator produces code once; the output is then yours to own and edit (scaffolding a new project). An active generator produces code that is regenerated whenever the specification changes; the output must never be edited (an ORM mapping, an API client). Confusing the two is the commonest and most expensive mistake in this area.

By technique

  • Template-based — a template plus data. Jinja2, Velocity, Mustache, ERB.
  • Model-driven (MDA/MDE) — code from an abstract model such as UML.
  • Compiler / transpiler — the oldest generator of all: source in, lower-level source or machine code out. TypeScript→JS, Babel, protoc.
  • Metaprogramming — code generated at compile or run time from within the language: C macros, C++ templates, Java annotation processors, Python metaclasses, Rust macros.

By what they produce

  • Scaffolding — a whole project skeleton. rails new, create-react-app, mvn archetype:generate, Yeoman, Cookiecutter.
  • Data-access / ORM — entity classes from a database schema, or DDL from entities. Hibernate, Django, Entity Framework.
  • Interface / API — clients, servers and stubs from a contract. OpenAPI Generator, gRPC/protobuf, GraphQL codegen, WSDL, Thrift.
  • Parsers — from a grammar. Lex/Yacc, ANTLR, Bison.
  • GUI builders — layout code from a visual designer.
  • Test and mock generation — stubs, fuzz corpora, property tests.

Generation in the DevOps toolchain

  • Infrastructure as code — Terraform, CloudFormation and Helm all generate configuration or API calls from declarative source.
  • Configuration management — Ansible, Puppet and Chef generate config files from templates plus host variables. You will do exactly this by hand in Unit 2.
  • Pipeline generation — templated CI files across many repositories.
  • AI-assisted generation — Copilot-class tools generate plausible code statistically rather than deterministically. Everything above is reproducible and reviewable as a specification; AI output is neither, so it must be reviewed and tested as if a stranger had written it. Useful; not in the same category.

Unit 1 in one paragraph

A delivery pipeline moves a change from commit to user through gates ordered by cost. Automating it buys repeatability first and speed second, and the four delivery metrics make that gain visible. Because an automated deployment is a shared, readable artifact, it is also the practical hinge on which DevOps adoption turns. RAD depends on that same machinery — its prototype-driven loop only works when builds and deployments are free — and code generation is what makes the prototypes cheap enough to throw away.
