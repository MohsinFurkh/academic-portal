Part A · what cron is

Introduction to cron and crontab

cron is the time-based job scheduler daemon — crond — that has been part of Unix since the 1970s. It wakes every minute, compares the time against every scheduled entry, and runs the ones that match.

crontab is two things, which is a permanent source of confusion:

  • The file — the table of "cron tab"le entries belonging to a user.
  • The command — crontab(1), which you use to install, list and edit that file. You do not edit the file directly; the command validates your entry and tells the daemon to reload.

Its defining properties

  • Minute granularity. Nothing finer, ever.
  • Fire and forget. cron starts the job; it does not track, retry or supervise it.
  • No catch-up. If the machine was off at 02:30, that run simply did not happen. (anacron exists for exactly this, on laptops and desktops.)
  • No dependencies. "Run B after A succeeds" is not something cron can express.

Scope — where cron entries live

LocationOwnerHas user field?
crontab -e → /var/spool/cron/…One user, their own jobsNo
/etc/crontabSystem-wide, root-managedYes
/etc/cron.d/*System-wide, one file per package or serviceYes
/etc/cron.{hourly,daily,weekly,monthly}/Drop an executable script in; no schedule line at alln/a

The user field is the trap. A line copied from your personal crontab into /etc/cron.d/ is now missing a field, so cron reads your command as the username, and the job never runs. Copying the other way silently runs your job as the wrong user.

For deployment, prefer /etc/cron.d/: it is a plain file, so it can live in Git, be reviewed, and be installed by your configuration management. A personal crontab is invisible to everyone else and disappears with the account. Access is controlled by /etc/cron.allow and /etc/cron.deny.

Part A · what cron is

Use-cases of crontab, and its limits

What cron is good at

  • Maintenance — log rotation, retention purges, cache clearing, trash expiry.
  • Backups — nightly dumps, weekly full copies, off-site sync.
  • Reporting — the daily summary email from Lecture 3.
  • Monitoring — disk alarms, health checks, certificate expiry warnings.
  • Batch processing — nightly imports, invoice generation, reindexing.
  • Synchronisation — pulling a vendor feed, pushing metrics, renewing certificates.

The common shape: periodic, independent, idempotent, and tolerant of being a few minutes late.

Where cron is the wrong tool

  • Sub-minute work. Use a systemd timer, or a daemon with a sleep loop.
  • Event-driven work. "When a file arrives" is inotify or a queue, not a poll every minute.
  • Workflows with dependencies or retries. Use Airflow, Argo, Jenkins — cron has no concept of "after", "on failure" or "retry".
  • Long-running services. That is systemd's job, not cron's.
  • Clustered jobs. Put the same cron entry on three servers and it runs three times. You need a distributed lock or a leader.

cron vs systemd timers

Modern distributions increasingly prefer systemd timers. They cost more configuration — two unit files instead of one line — and buy real advantages:

  • Persistent=true catches up missed runs after downtime.
  • RandomizedDelaySec spreads load across a fleet.
  • Resource limits, sandboxing, dependencies, and proper journal integration.
  • systemctl list-timers shows the next run of everything.

Learn cron anyway. It is on every Unix machine you will ever touch, it is in every legacy system you will inherit, and its syntax appears in Kubernetes CronJobs, cloud schedulers and CI tools everywhere.

a-b/nstepped range0 8-18/2 * * * every 2 h in work hours

Shortcuts

@reboot once at start-up · @hourly = 0 * * * * · @daily/@midnight = 0 0 * * * · @weekly = 0 0 * * 0 · @monthly = 0 0 1 * * · @yearly = 0 0 1 1 *

The three things that catch everyone

1 · Day-of-month and day-of-week are OR, not AND. This is the great cron trap:

0 0 13 * 5     # NOT "Friday the 13th"
               # It runs on the 13th of EVERY month,
               # AND on EVERY Friday.

When both fields are restricted, cron takes the union. If one of them is *, the other simply applies. To get a real Friday-the-13th, test inside the script: [[ $(date +\%u) == 5 ]] || exit 0.

2 · % is special. In a crontab, an unescaped % becomes a newline and everything after the first one is fed to the command as standard input. So date +%F breaks. Write date +\%F, or — far better — put the command in a script and keep the crontab line trivial.

3 · Fields are AND-ed otherwise. 30 2 * * 1 is 02:30 and Monday, not 02:30 or Monday.

Part C · writing tasks

Why it works in your shell and not in cron

cron's environment is almost empty

Your interactive shell has read /etc/profile, ~/.bash_profile and ~/.bashrc, and has a rich PATH, your aliases, your virtualenv, your JAVA_HOME, your locale. cron reads none of it. A cron job typically starts with roughly:

SHELL=/bin/sh
PATH=/usr/bin:/bin
HOME=/home/user
LOGNAME=user
# and essentially nothing else.
# No DISPLAY, no LANG, no virtualenv, no aliases,
# no tty — so anything that prompts will hang.

Consequences: python is not found because it lives in /usr/local/bin; SHELL=/bin/sh means bash-only syntax such as [[ ]] or arrays fails; a relative path resolves against $HOME, not where you thought; and a job that asks a question waits for an answer that never comes.

Four rules that eliminate the whole class

  1. Absolute paths everywhere — for the script, its inputs, its outputs and the binaries it calls. Or set PATH explicitly at the top of the crontab.
  2. Put the logic in a script, not in the crontab line. The crontab should contain a schedule and one absolute path. This also solves the % problem and makes the job testable.
  3. Declare your environment inside the script — the shebang fixes the interpreter, and anything you need (PATH, LANG, a virtualenv activation) is set explicitly. Never rely on inheritance.
  4. Test it the way cron will run it: env -i /bin/sh -c '/opt/scripts/backup.sh' — an empty environment. If it survives that, cron will not surprise you.

Also worth setting at the top of a crontab: SHELL=/bin/bash, PATH=..., MAILTO=ops@example.com (cron emails any output to this address; MAILTO="" disables it), and CRON_TZ if the entry must not follow the system time zone.

Part C · writing tasks

Slide 2, repaired — count how many you found

# /etc/cron.d/appdb-backup    (root-owned, mode 0644, in Git)
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=ops@example.com

#  m  h dom mon dow  user     command
  30  2  *   *   *   backup   /usr/bin/flock -n /var/lock/appdb-backup.lock \
                              /opt/scripts/backup.sh --db appdb \
                              >> /var/log/appdb-backup.log 2>&1

The seven defects, and their fixes

  1. cd ~/scripts && ./backup.sh — relative path, and if the cd fails the && silently skips the job. → absolute path.
  2. No PATH — the script's own commands may not be found. → set it.
  3. SHELL=/bin/sh by default — bash syntax breaks. → set it.
  4. > backup.log — writes to $HOME, and overwrites yesterday's log. → >> to an absolute path.
  5. 2>&1 missing — stderr is not redirected, so cron emails it, and if mail is not configured the error message is destroyed. This is the reason most failing cron jobs fail silently.
  6. No overlap protection — a run that takes 40 minutes eventually collides with the next. → flock -n exits immediately if the lock is held.
  7. Runs as a human user, whose account will one day be disabled. → a dedicated service account, in /etc/cron.d, under version control.

Two more you should add

Log rotation for your own log. >> grows forever — this is the log file that fills the disk at 4 a.m. and takes the database with it. Add a /etc/logrotate.d/ entry.

Alert on the absence of success. MAILTO only tells you when the job produces output. If cron itself is stopped, or the entry is deleted, or the machine is off, you get nothing at all. Have the script touch a heartbeat file or ping a monitoring endpoint, and alert when it goes stale.

Spread the load. Everyone writes 0 0 * * *, so every job on every server starts at midnight together. Offset your schedules (17 2 * * *), or add a random sleep of up to a few minutes at the top of the script.

Part D · managing

Editing and updating the crontab

crontab -e                # edit your crontab (validated on save)
crontab -l                # list it
crontab -l > ~/cron.bak    # BACK IT UP — do this first, always
crontab -r                # DELETE it entirely. No confirmation. None.
crontab ~/cron.txt        # install from a file (replaces everything)

sudo crontab -l -u backup # another user's crontab
sudo crontab -e -u backup

EDITOR=nano crontab -e    # if vi is not your friend today

crontab -r is one keystroke from crontab -e on a US keyboard, deletes everything instantly and asks nothing. Countless schedules have died this way. Defend yourself: keep the authoritative copy in Git, and crontab -l > backup before every edit. Some people alias crontab to crontab -i.

The professional workflow

Do not hand-edit crontabs on servers. Treat the schedule as code:

  1. The entry lives in a file in the repository — deploy/cron.d/appdb-backup.
  2. Code review changes to it like any other change.
  3. Deployment installs it to /etc/cron.d/ with the right owner and mode (0644, root-owned — cron refuses group- or world-writable files, silently).
  4. The file ends with a newline. A crontab file whose last line has no newline is ignored by some cron implementations — a genuinely maddening bug.

Test before you wait. Never verify a nightly job by waiting until tonight:

# 1. run it exactly as cron would
sudo -u backup env -i /bin/sh -c '/opt/scripts/backup.sh'

# 2. schedule it two minutes out, watch, then set the real time
*/2 * * * * backup /opt/scripts/backup.sh >>/tmp/t.log 2>&1
Part D · managing

Seeing what cron actually did

Finding every scheduled job on a host

# Every user's crontab, not just yours
for u in $(cut -f1 -d: /etc/passwd); do
    echo "### $u"; crontab -l -u "$u" 2>/dev/null
done

# The system locations — people forget these exist
cat /etc/crontab
ls -l /etc/cron.d/ /etc/cron.{hourly,daily,weekly,monthly}/

# And the other scheduler, which is where new jobs increasingly live
systemctl list-timers --all

"Something runs at 3 a.m. and nobody knows what" is a real support ticket. These four commands are the answer, and the last one is the one people forget.

Reading cron's own log

# systemd distributions
journalctl -u cron --since "today"       # Debian/Ubuntu
journalctl -u crond --since "today"      # RHEL/Fedora

# older systems
grep CRON /var/log/syslog
tail -f /var/log/cron

# is the daemon even running?
systemctl status cron

Read the log carefully — it tells you less than you expect. cron logs that it started a command. It does not log the exit status, and it does not log the output. So a line saying CMD (/opt/scripts/backup.sh) proves only that cron tried; the script may have died on its first line.

Therefore your job must log for itself: redirect >> logfile 2>&1, print a start and an end line with timestamps, exit with a meaningful status, and logger anything important into the journal.

The debugging checklist, in order. ① Is the daemon running? ② Is the entry actually installed (crontab -l, /etc/cron.d)? ③ Does the log show cron starting it? If not, the schedule or the file permissions are wrong. If yes, the script itself failed → ④ run it under env -i; ⑤ check absolute paths and SHELL/PATH; ⑥ check the user's permissions on every file it touches; ⑦ check 2>&1 is present, because you are probably throwing away the error message that would have told you all this.

Unit 3 in six sentences

  1. cron runs commands on a minute-granularity schedule, fire-and-forget, with no retries, no dependencies and no catch-up.
  2. Entries live in a user crontab, in /etc/crontab, in /etc/cron.d or in the cron.daily-style directories — and only the system ones carry a user field.
  3. Five fields, and day-of-month with day-of-week is an OR.
  4. cron's environment is nearly empty, so absolute paths and an explicit PATH/SHELL are mandatory.
  5. Redirect both streams, lock against overlap, run as a service account, and keep the entry in version control.
  6. cron logs that it started your job and nothing else — so your job must log for itself, and something must alert when it stops succeeding.
