Scenario 5

Ensure the web server is running

The naive version, and why it is wrong

pgrep nginx || systemctl start nginx
  • A running process is not a working service. nginx can be alive and returning 502 for every request because its backend is down. You must test behaviour, not existence.
  • pgrep nginx matches too much — including your own editor session named vim nginx.conf. Use pgrep -x, or better, ask systemd.
  • It restarts forever. If nginx dies because of a bad config, this loop restarts it every minute all night, filling logs and hiding the real fault.
  • It tells nobody. A service that silently restarts 400 times looks healthy on a dashboard.

The version you would put on a real host

#!/usr/bin/env bash
set -uo pipefail
URL="http://127.0.0.1/healthz";  SVC=nginx
STATE=/var/lib/watchdog/$SVC.fails;  MAX=3

# Behavioural check: real request, short timeout, expect 200
if curl -fsS --max-time 5 "$URL" >/dev/null; then
    echo 0 > "$STATE"; exit 0
fi

fails=$(< "$STATE"); fails=$(( fails + 1 ))
echo "$fails" > "$STATE"
logger -t watchdog -p daemon.err "$SVC health check failed ($fails/$MAX)"

if (( fails >= MAX )); then
    logger -t watchdog -p daemon.crit "$SVC: giving up, paging on-call"
    notify-oncall "$SVC down on $(hostname -f) after $fails checks"
    exit 1                       # STOP restarting; a human is needed
fi

nginx -t && systemctl restart "$SVC"   # validate config BEFORE restarting

In production, let the init system do it. systemd already restarts crashed services with back-off: Restart=on-failure, RestartSec=5, StartLimitBurst=3, StartLimitIntervalSec=60. A script like the one above is for the case systemd cannot see — the process is alive but not serving. The three ideas to carry away: check behaviour, back off after repeated failures, and escalate to a human.

Scenario 6

User command validation — the answers to slide 2

Five defects in eleven lines

  • Empty input. Press Enter twice and the script runs rm -rf / — the unquoted $dir/$pattern becomes just /.
  • Command injection. Input . ; rm -rf ~. Because the variable is unquoted and the value is re-parsed by the shell, your semicolon becomes a command separator.
  • Word splitting. /var/my logs becomes two arguments — rm -rf /var/my and logs.
  • Path traversal. ../../etc escapes wherever you thought you were.
  • No confirmation, no dry run, no log. Nothing records what was destroyed.

The validation rules

  • Quote every expansion. "$dir", always. This one habit removes two of the five defects above.
  • Allow-list, never block-list. Do not try to strip dangerous characters — you will miss one. Accept only what matches a pattern you defined.
  • Validate type, range and existence before use: is it a directory? is it under the permitted root? is the number actually a number?
  • Canonicalise before comparing. realpath resolves .. and symlinks, so your "is it inside /var/tmp" check cannot be fooled.
  • Never eval user input, and never build a command string from it. Pass values as arguments, not as text to be re-parsed.
  • Confirm destructive actions, and refuse them entirely when not on a terminal.
# The repaired core
ALLOWED_ROOT=/var/tmp/cleanup

read -r -p "Directory: " dir
[[ -n "$dir" ]]                     || { echo "empty input" >&2; exit 2; }
[[ "$dir" =~ ^[A-Za-z0-9_/.-]+$ ]] || { echo "illegal characters" >&2; exit 2; }
dir=$(realpath -e -- "$dir")       # resolves .. and symlinks; -e = must exist
[[ "$dir" == "$ALLOWED_ROOT"/* ]]   || { echo "outside allowed root" >&2; exit 2; }

read -r -p "Delete everything under $dir? type YES: " ok
[[ "$ok" == "YES" ]]              || { echo "aborted"; exit 0; }

logger -t cleanup "$USER purging $dir"
find "$dir" -mindepth 1 -delete   # note: not `rm -rf "$dir"/*` — no glob surprises

The mental model: in a shell, an unquoted variable is not a value — it is text that the shell will re-read as syntax. Every shell injection bug in existence follows from forgetting that sentence.

Scenario 7

Disk usage alarm

#!/usr/bin/env bash
set -uo pipefail
THRESHOLD=${1:-85}
STATE_DIR=/var/lib/diskalarm; mkdir -p "$STATE_DIR"

# -P forces POSIX single-line output; without it long device names wrap and break awk.
# -x excludes pseudo-filesystems that are always "100% full" and always fine.
df -P -x tmpfs -x devtmpfs -x squashfs | awk 'NR>1 {gsub(/%/,"",$5); print $5, $6, $4}' |
while read -r pct mount avail; do
    flag="$STATE_DIR/$(systemd-escape "$mount")"
    if (( pct >= THRESHOLD )); then
        # Alert once per crossing, not once per run — otherwise 96 emails a day.
        if [[ ! -e "$flag" ]]; then
            echo "$mount at ${pct}% (only ${avail}K free) on $(hostname -f)" |
                mail -s "[DISK] $(hostname -s) $mount ${pct}%" ops@example.com
            date -Is > "$flag"
        fi
    elif (( pct < THRESHOLD - 5 )); then
        # Hysteresis: clear only well below the line, so a filesystem hovering
        # at exactly 85% does not alternate alert/clear every five minutes.
        [[ -e "$flag" ]] && { echo "$mount recovered: ${pct}%" | mail -s "[OK] $mount" ops@example.com; rm -f "$flag"; }
    fi
done

Three ideas doing the work

  • State on disk so the script knows whether it has already complained. Without it, an alert every five minutes trains the team to filter your emails, and then they miss the important one.
  • Hysteresis — a different threshold for clearing than for firing — stops alert flapping.
  • Report free space as well as percentage. 90% of 40 GB is comfortable; 90% of a 20 GB root disk is two hours from an outage.

The failure nobody expects: inodes

A filesystem can be 20% full and still refuse to create a file, because it has run out of inodes — typically a directory holding millions of tiny session or cache files. df -h looks fine; df -i shows 100%. Check both. This is a classic "the disk isn't full, but nothing works" incident.

Better than a threshold

85% is arbitrary. What operators actually need is time to exhaustion: record usage each run, fit the recent trend and alert when the disk will be full within, say, four hours. A slow leak at 60% that fills in three hours matters far more than a stable 88%. This is what production monitoring tools compute for you — but knowing why is the point.

Scenario 8 · part 1

Sending files to a recycle bin

rm is final. There is no undelete on ext4 worth relying on. So: intercept deletion, move the file aside, and keep enough metadata to put it back.

#!/usr/bin/env bash
# trash — move files to a recycle bin instead of destroying them
set -euo pipefail
TRASH="${TRASH_DIR:-$HOME/.local/share/Trash}"
mkdir -p "$TRASH/files" "$TRASH/info"

(( $# )) || { echo "usage: trash FILE..." >&2; exit 2; }

for target in "$@"; do
    [[ -e "$target" || -L "$target" ]] || { echo "no such file: $target" >&2; continue; }

    src=$(realpath -s -- "$target")            # -s: do not follow the final symlink
    base=$(basename -- "$src")
    id="${base}.$(date +%Y%m%d-%H%M%S).$$"       # collision-proof: two deletes of
                                                # the same name must not overwrite
    # The info file is what makes RESTORE possible at all.
    { echo "Path=$src"
      echo "DeletionDate=$(date -Is)"
      echo "DeletedBy=$USER"
      echo "Mode=$(stat -c '%a' -- "$src")"
      echo "Owner=$(stat -c '%U:%G' -- "$src")"
    } > "$TRASH/info/$id.info"

    mv -- "$src" "$TRASH/files/$id"
    logger -t trash "$USER trashed $src as $id"
    echo "trashed: $src"
done

Why -- everywhere

It ends option parsing. Without it, a file literally named -rf or --help is read as a flag by mv. Attackers and clumsy users both create such names; -- costs nothing.

The cross-filesystem catch

mv within one filesystem is an instant rename. Across filesystems it becomes copy-then-delete — slow for large files, and it can fill the trash volume. Either keep a trash directory per filesystem, or refuse and warn when stat -c %d differs.

Deploying it

Put it in ~/bin or /usr/local/bin. Do not alias rm to it. Aliases do not apply in scripts or over ssh, so you get a false sense of safety and a nasty surprise. Train the habit of typing trash instead.

Scenario 8 · part 2

Restoring files, and the delete audit trail

Restore — the reason the info file exists

# untrash — list and restore
case "${1:-list}" in
  list)
     for i in "$TRASH"/info/*.info; do
        [[ -e "$i" ]] || break
        id=$(basename "$i" .info)
        printf '%-40s %s\n' "$id" "$(sed -n 's/^Path=//p' "$i")"
     done ;;
  restore)
     id="${2:?which id? run: untrash list}"
     info="$TRASH/info/$id.info"
     [[ -f "$info" ]] || { echo "unknown id" >&2; exit 1; }
     dest=$(sed -n 's/^Path=//p' "$info")
     [[ -e "$dest" ]] && { echo "$dest exists; refusing" >&2; exit 1; }
     mkdir -p "$(dirname "$dest")"
     mv -- "$TRASH/files/$id" "$dest"
     chmod "$(sed -n 's/^Mode=//p' "$info")" -- "$dest"
     rm -f "$info"
     logger -t trash "$USER restored $dest" ;;
esac

Note the refusal to overwrite an existing destination: a restore that silently clobbers a newer file has caused more data loss than the original delete.

Logging delete actions

Both scripts call logger, which writes to syslog with a tag, so entries land in the journal alongside everything else and are picked up by log shipping automatically:

journalctl -t trash --since "2 days ago"

What a delete audit record must contain: who, what (full original path), when (ISO-8601), from where (tty, ssh client), and the result. That is the difference between "some files went missing" and a five-minute answer.

Expiry closes the loop. A trash directory that is never emptied is just a slower disk-full incident. Reuse Lecture 3's retention pattern — purge trashed items older than 30 days, log every purge, and keep the info files a little longer than the data so you can still say what was removed.

Note: logger is not tamper-proof — a user who can delete files can usually also write misleading log lines. Real auditing ships logs off-host immediately, and uses auditd rules for kernel-level file events.

Build it, then try to break it

1 · Make it work 2 · Attack your own script 3 · Fix what you broke 10:00

Build

  1. Write trash and untrash as above into ~/bin, and make them executable.
  2. Trash three files, list them, restore one, confirm its permissions came back with ls -l.
  3. Add a --empty N mode that purges items older than N days and logs each purge.

Attack — every one of these must be handled

  1. trash with no arguments.
  2. trash "my report.txt" — a name with a space.
  3. touch -- -rf && trash -- -rf — a name that looks like a flag.
  4. Trash two different files that share a basename, from different directories. Both must survive and both must restore to the right place.
  5. Trash a file, recreate a file at the same path, then restore. The script must refuse rather than overwrite.
  6. Trash a symlink. The link should move — not its target.

Test 4 is the one most student scripts fail. That is what the timestamp-and-PID suffix in the id is defending against.

Scripts that act on the system need three things scripts that report do not

1 · A validated input boundary

Allow-list the input, quote every expansion, canonicalise paths and confine them to a permitted root. Everything past that boundary can then be trusted.

2 · A limit on its own zeal

Back off after repeated failures, alert once per crossing not once per run, and escalate to a human instead of retrying forever. An automation that never gives up is an automation that hides faults.

3 · A way back

Trash instead of delete, refuse to overwrite on restore, and log who did what to which path and when. Reversibility is a feature you build, not a hope.
