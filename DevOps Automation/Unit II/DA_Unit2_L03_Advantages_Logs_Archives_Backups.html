Part A · why

Advantages of automation

Correctness

  • Consistency — identical execution every time, on every host.
  • Fewer errors — no mistyped path, no forgotten step, no wrong server at 2 a.m.
  • Testable — a script can be run in a sandbox; a habit cannot.
  • Reviewable — it goes through Git and code review like any other code.

Capacity

  • Speed — seconds instead of an afternoon.
  • Scale — the same script serves 1 server or 500. This is the advantage with no manual equivalent at all.
  • Availability — it runs at 03:00 on a Sunday without complaint.
  • Parallelism — do twenty hosts at once.
  • People freed for work that needs judgement.

Governance

  • Executable documentation — the script is the procedure, and it cannot go stale without failing.
  • Auditability — logged, timestamped, attributable runs.
  • Knowledge retention — the procedure survives the person who wrote it.
  • Lower cost — engineer hours, and the outages that no longer happen.

The honest counterweight. Automation has costs: it must be written, tested and maintained; a bug now executes at machine speed on every host at once; and skills atrophy when nobody remembers the manual procedure. An automated wrong action is far more damaging than a manual one — which is why the rest of this unit insists on dry-run modes, checks before destructive steps, and logging.

The scoring rule — automate where all four are high: frequency (how often), determinism (are the rules fixed?), error-proneness (what does a mistake cost?), tedium (does attention drift?). By that rule: 1, 3, 5 and 6 are prime; 2, 4 and 8 need judgement and cannot be automated at all — you automate the data-gathering around them. Number 7 is the interesting one: it is once-only, so the payback looks negative — but scripting it still gives you a dry run, a repeatable retry after failure, and a record of what was done. Automate one-offs when getting them wrong is expensive.

Scenario 1

Archiving logs

The problem

A busy web server writes hundreds of megabytes of log a day. Left alone, three things happen: the disk fills and the service dies; the file becomes too large to search; and nobody can find last Tuesday's entries.

The shape of the solution

  1. Every night, take the current log and roll it to a dated name.
  2. Compress it — text logs compress by 90% or more.
  3. Signal the service to reopen its log file, or the process keeps writing to the file you just moved.
  4. Move the archive to an archive directory (or object storage).
  5. Verify the archive is readable before considering the job done.

Step 3 is the one that catches everybody

On Linux, a running process holds an open file descriptor, not a filename. Rename access.log and nginx happily keeps writing to the renamed inode — your "archive" grows all day and the new access.log stays empty. Worse, if you delete it, the space is not reclaimed until the process exits, so df shows a full disk while du shows nothing.

The fix: after rolling, send the daemon the signal that makes it reopen its logs (nginx -s reopen, systemctl reload, or kill -USR1), or use copytruncate, which copies the file and truncates the original in place — at the cost of losing any lines written during the copy.

#!/usr/bin/env bash
set -euo pipefail

LOG_DIR=/var/log/nginx;  ARCHIVE_DIR=/var/archive/nginx
STAMP=$(date +%F)                       # 2026-09-03 — sorts correctly, always

mkdir -p "$ARCHIVE_DIR"
for f in "$LOG_DIR"/*.log; do
    [[ -s "$f" ]] || continue                    # skip empty logs
    base=$(basename "$f" .log)
    mv "$f" "$ARCHIVE_DIR/${base}-${STAMP}.log"
done

nginx -s reopen                              # CRITICAL: make nginx reopen its files
gzip -9 "$ARCHIVE_DIR"/*-"$STAMP".log
gzip -t "$ARCHIVE_DIR"/*-"$STAMP".log.gz    # verify: an unverified archive is a rumour

In production, prefer logrotate — it already handles rolling, compression, signalling, retention and error cases, and it is declarative: /etc/logrotate.d/nginx. Write the script once to understand what logrotate is doing for you; then use logrotate. Knowing when not to write a script is part of the skill.

Scenario 2

Auto-discard old archives — the most dangerous script you will write

The task

Archiving without expiry only delays the disk-full incident. A retention policy answers one question: how long must we be able to look back? Usually set by law or contract, not by engineering taste (audit logs 1–7 years; web logs 30–90 days; backups on a grandfather-father-son cycle).

# The core idea, and note the ORDER of the tests
find "$ARCHIVE_DIR" \
     -maxdepth 1 -type f -name '*.log.gz' \
     -mtime +30 -print -delete

-maxdepth 1 do not recurse into other people's directories · -type f never match a directory · -name narrow to files you created · -mtime +30 modified more than 30×24 h ago · -print before -delete so the log records what went.

Four rules, learned the hard way

  • Always run it as a dry run first. Replace -delete with -print and read every line. Do this on the real server, not just your laptop.
  • Never let the directory be empty or unset. If $ARCHIVE_DIR is unset, find "" -delete or find / -delete is what you have written. set -u plus ${ARCHIVE_DIR:?not set} prevents this, and it is the single most valuable habit in this lecture.
  • Filter by name, not only by age. -name '*.log.gz' means a mistake in the path still cannot delete somebody's photos.
  • Log every deletion, and alert if the count is wildly different from yesterday's — a sudden jump from 1 file to 4,000 means your date logic is wrong, and that alert is the only thing standing between you and a very bad morning.

Prefer moving to a trash directory over deleting outright — Lecture 4 builds exactly that.

Watch the units: -mtime +30 counts 24-hour periods and truncates, so it means "at least 31 days old". -mmin counts minutes. And -atime (access time) is unreliable on modern mounts because of relatime — always retain on -mtime.

Scenario 3

MySQL (RDBMS) backups

#!/usr/bin/env bash
set -euo pipefail

DB="${1:?usage: backup-db.sh <database>}"
DEST=/var/backups/mysql;  STAMP=$(date +%F_%H%M)
OUT="$DEST/${DB}-${STAMP}.sql.gz"

mkdir -p "$DEST"

# --defaults-extra-file holds the credentials, chmod 600, owned by the backup user.
# NEVER put a password on the command line: it is visible in `ps` to every user.
mysqldump --defaults-extra-file=/etc/mysql/backup.cnf \
          --single-transaction --quick --routines --triggers --events \
          --set-gtid-purged=OFF "$DB" \
    | gzip -9 > "$OUT"

gzip -t "$OUT"                                # 1. is the archive intact?
[[ $(stat -c%s "$OUT") -gt 1024 ]]           # 2. is it plausibly non-empty?
zcat "$OUT" | tail -1 | grep -q 'Dump completed'  # 3. did the dump FINISH?

logger -t db-backup "ok $DB -> $OUT ($(du -h "$OUT" | cut -f1))"

Why those flags

  • --single-transaction — a consistent snapshot on InnoDB without locking the tables, so the site stays up. Without it you either lock users out or get a dump that is internally inconsistent.
  • --quick — stream rows instead of buffering a huge table in memory.
  • --routines --triggers --events — not included by default; restore without them and the schema is silently incomplete.
  • Pipe straight into gzip — never write the plaintext dump to disk first.

The part everyone skips

A backup that has never been restored is not a backup. The three checks above prove the file is sound; they do not prove the data is. Once a month, automatically restore the latest dump into a scratch database and run a query that counts rows in three key tables. Almost every catastrophic data-loss story ends with the sentence "the backups had been failing silently for months".

The rest of a real policy

  • 3-2-1: three copies, two media, one off-site. A backup on the same disk as the database is not a backup.
  • Encrypt dumps at rest — they contain everything you have promised to protect.
  • Retention: daily 7, weekly 4, monthly 12 — reuse Scenario 2, per class.
  • Alert on absence. Silence is the failure mode: page someone if no successful backup has been recorded in 26 hours.
  • For large databases, add binary-log shipping for point-in-time recovery; a nightly dump means you can lose up to a day.
Scenario 4

Email a web server summary

Turn last night's access log into six numbers a human will actually read over coffee. This is the reporting pattern: gather → summarise → deliver → repeat on a schedule.

#!/usr/bin/env bash
set -euo pipefail
LOG=/var/archive/nginx/access-$(date -d yesterday +%F).log.gz
REPORT=$(mktemp);  trap 'rm -f "$REPORT"' EXIT   # always clean up

{
  echo "Web summary for $(date -d yesterday +%F) on $(hostname -f)"
  echo
  echo "Total requests : $(zcat "$LOG" | wc -l)"
  echo "Unique clients : $(zcat "$LOG" | awk '{print $1}' | sort -u | wc -l)"
  echo "Bytes served   : $(zcat "$LOG" | awk '{s+=$10} END {printf "%.2f GB", s/1073741824}')"
  echo
  echo "Status codes:"
  zcat "$LOG" | awk '{c[$9]++} END {for (k in c) printf "  %-5s %8d\n", k, c[k]}' | sort
  echo
  echo "Top 10 URLs:"
  zcat "$LOG" | awk '{print $7}' | sort | uniq -c | sort -rn | head -10
  echo
  echo "Top 10 clients by 4xx/5xx:"
  zcat "$LOG" | awk '$9 >= 400 {print $1}' | sort | uniq -c | sort -rn | head -10
} > "$REPORT"

mail -s "[$(hostname -s)] web summary $(date -d yesterday +%F)" ops@example.com < "$REPORT"

The awk idiom worth memorising

{c[$9]++} END {for (k in c) print k, c[k]} — a one-line group-by-and-count over any column of any log. Change $9 and you have counted anything. Combined with sort | uniq -c | sort -rn | head, this pair answers most "what is happening on my server" questions without any tooling at all.

Making the report actually useful

  • Compare with yesterday. "412,000 requests" means nothing; "412,000, up 38%" is a story. Store yesterday's numbers in a file and print the delta.
  • Send failures loudly, successes quietly. A daily green email trains people to filter it, and then the red one is filtered too. Report by exception where you can.
  • Use a real transport in production: a local mail command usually lands in spam. Send via the organisation's SMTP relay or an API, or post to Slack/Teams.
  • Never email log contents containing user data or tokens.

Build and test a retention script — safely

1 · Build the fixture 2 · Dry run 3 · Only then delete 8:00

Step 1 — make a safe playground with fake dates

mkdir -p ~/lab/archive && cd ~/lab/archive
for d in 1 5 20 31 45 90; do
    f=access-$(date -d "$d days ago" +%F).log.gz
    echo fake > "$f"
    touch -d "$d days ago" "$f"     # backdate mtime
done
echo keepme > important.txt; touch -d '200 days ago' important.txt
ls -l

touch -d is how you test time-based logic without waiting a month. Note the decoy: important.txt is the oldest file in the directory and must survive.

Step 2 — your tasks

  1. Write a find that lists the .log.gz files older than 30 days. Confirm exactly three match, and that important.txt is not among them.
  2. Add -delete. Re-run ls -l and confirm.
  3. Wrap it in a script that takes the directory and the age as arguments, refuses to run if the directory is unset or does not exist, prints each deletion, and exits non-zero on failure. Start it with set -euo pipefail.
  4. Stretch: add a --dry-run flag that prints what would be deleted and changes nothing. Make it the default, so deletion requires an explicit --force.

Point 4 is the professional habit: destructive by request, never destructive by default. Bring your script to Lecture 4.

Four scenarios, one shape

Every scenario today was: select the inputs → transform them → verify the result → record what happened → alert if it did not.

The commands change; the shape does not. When you meet an unfamiliar automation task, write those five lines as comments first and fill them in. The two students always forget are verify and alert — and those two are the difference between a script and an unattended script.

What you should be able to do now

  • Explain why a rolled log needs the daemon signalled, and what happens if it is not.
  • Write a retention find that cannot delete the wrong thing.
  • Take a consistent, verified, credential-safe MySQL dump — and say why an unrestored backup does not count.
  • Summarise any log column with one awk idiom.
