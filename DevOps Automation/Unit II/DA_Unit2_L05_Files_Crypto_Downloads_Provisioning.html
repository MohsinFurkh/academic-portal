Scenario 9

File formatter

Two different jobs share this name. Know which one you are doing.

A · Normalising messy text and data files

# Strip Windows CR, trailing spaces and blank runs; align columns
sed -i 's/\r$//; s/[[:space:]]*$//' data.csv
cat -s report.txt | fmt -w 78 > report.clean.txt
column -t -s, data.csv | head            # readable table preview

# Reformat a fixed-width extract into CSV with awk
awk '{ printf "%s,%s,%.2f\n", $1, $2, $3 }' extract.txt > out.csv

# Pretty-print structured data — never with sed
jq . config.json > config.pretty.json
yq -P . values.yaml

The stray \r is the single most common cause of "the script works on my laptop but the server says bad interpreter: /bin/bash^M". A file edited on Windows carries CRLF line endings; run file or dos2unix before believing anything else.

B · Formatting source code — do this in the pipeline

Every language has a canonical formatter: black (Python), prettier (JS/TS/CSS), gofmt (Go), clang-format (C/C++), shfmt (shell). Automating them removes an entire category of pointless code review.

  • Locally: a Git pre-commit hook formats staged files.
  • In CI: run the formatter in check mode (black --check) and fail the build on a difference. Checking is better than rewriting in CI — a pipeline that pushes commits back to your branch is a pipeline that will surprise someone.
  • Format the whole repository in one commit, then add the check. A gradual rollout means every diff is polluted with formatting noise forever.

The point is not beauty. It is that a mechanical, unarguable rule is applied identically to everyone, so reviewers spend their attention on logic instead of on brace placement.

Scenario 10

Decrypting files in an automated job

#!/usr/bin/env bash
set -euo pipefail
umask 077                                     # anything we create is 0600 from birth

IN="${1:?usage: decrypt.sh <file.gpg>}"
WORK=$(mktemp -d)
trap 'rm -rf -- "$WORK"' EXIT INT TERM        # plaintext dies with the script,
                                              # even on Ctrl-C or a failure

# Passphrase from a 0600 file or an agent — NEVER an argument, NEVER hardcoded.
gpg --quiet --batch --yes \
    --passphrase-file /etc/creds/vendor.pass \
    --decrypt --output "$WORK/payload.csv" -- "$IN"

# Verify the signature too: decryption proves secrecy, not authenticity.
gpg --verify -- "$IN" 2>/dev/null || { echo "UNSIGNED or bad signature" >&2; exit 1; }

process-payload "$WORK/payload.csv"              # plaintext never leaves $WORK

Four ways people leak the key

  • On the command line — --passphrase 'hunter2' is visible in ps to every user on the host.
  • In the script, which is then committed to Git, where it lives in history forever. A deleted secret is a rotated secret or it is still a secret you have lost.
  • In an environment variable that a child process inherits and helpfully dumps into a crash log or an error report.
  • In the plaintext left behind in /tmp after the job failed halfway. Hence the trap.

Rules that hold everywhere

  • Decrypt to memory or to a private temp dir, never in place next to the ciphertext.
  • Stream where you can: gpg -d file.gpg | mysql db — the plaintext never touches a disk.
  • Least privilege: the decryption key belongs to a dedicated service account, and no human logs in as it.
  • Rotate keys on a schedule, and have a tested procedure for doing so.
  • Prefer a secret manager (Vault, AWS/GCP KMS, systemd credentials) over any file on disk.

Encryption ≠ authentication

Anyone can encrypt a file to your public key, including an attacker who wants you to process their data. Only a signature tells you who sent it. Automated pipelines that decrypt vendor files and act on the contents must verify the signature — and must treat "no signature" as a failure, not as a warning to be logged and ignored.

Scenario 11

Bulk file downloader

#!/usr/bin/env bash
# fetch-all.sh urls.txt outdir   — resumable, parallel, verified
set -euo pipefail
LIST="${1:?url list}";  OUT="${2:?output dir}";  JOBS="${JOBS:-4}"
mkdir -p "$OUT"

fetch_one() {
    local url="$1" out="$2"
    curl --fail --location --silent --show-error \
         --retry 5 --retry-delay 2 --retry-all-errors \
         --connect-timeout 10 --max-time 600 \
         --continue-at - \
         --remote-time \
         --output "$out/$(basename "${url%%\?*}")" \
         -- "$url"
}
export -f fetch_one

# -P runs JOBS in parallel; -n1 one URL per invocation.
# grep strips blank lines and # comments so the list file can be documented.
grep -Ev '^\s*(#|$)' "$LIST" |
    xargs -P "$JOBS" -n1 -I{} bash -c 'fetch_one "$@"' _ {} "$OUT"

# Integrity: a download that "succeeded" can still be a truncated file or an
# HTML error page saved with a .tar.gz name.
( cd "$OUT" && sha256sum -c SHA256SUMS ) || { echo "CHECKSUM FAILURE" >&2; exit 1; }

Why each flag is there

  • --fail — without it, curl exits 0 on a 404 and you save the error page. This single flag is the difference between a script that works and one that lies.
  • --location — follow redirects; most download URLs are one.
  • --retry / --retry-delay — networks fail transiently; retry is not optimism, it is correctness.
  • --continue-at - — resume a partial file instead of restarting a 4 GB download.
  • --max-time — bound the whole transfer so one stalled host cannot hang the job until the next cron run collides with it.

Be a good citizen

  • Keep parallelism modest (2–8). Forty parallel streams is indistinguishable from a denial-of-service attack, and you will be blocked.
  • Respect robots.txt, rate limits and terms of service, and identify yourself with a real --user-agent including a contact address.
  • Use conditional requests — curl -z file or wget --timestamping — so a re-run downloads only what changed.
  • Only download what you are authorised to. Automation makes it trivially easy to scrape at a scale that is a legal problem, not a technical one.

The simpler forms

# wget already reads a list
wget -i urls.txt -P out/ \
     -c -t 5 --timeout=30 \
     --no-verbose

# mirror a directory, only new files
wget -r -np -nH --cut-dirs=2 \
     -N -A '*.tar.gz' https://host/pkgs/

Reach for wget for recursive mirroring, and curl when you need control over a single request. For anything that must be reliable, add checksums.

Scenario 12

System information — the script you run first on any unfamiliar host

#!/usr/bin/env bash
set -uo pipefail

echo "=== identity ==="
hostname -f;  source /etc/os-release && echo "$PRETTY_NAME"
uname -r;     uptime -p;  echo "booted: $(uptime -s)"

echo "=== cpu ==="
lscpu | grep -E '^(Model name|Socket|Core|CPU\(s\))'
echo "load: $(cut -d' ' -f1-3 /proc/loadavg) over $(nproc) cpus"

echo "=== memory ==="
free -h

echo "=== disk ==="
df -hT -x tmpfs -x devtmpfs
df -i  -x tmpfs -x devtmpfs | awk 'NR==1 || $5+0 > 80'   # inode pressure

echo "=== network ==="
ip -brief address
ip route show default

echo "=== services and ports ==="
systemctl list-units --type=service --state=failed --no-pager
ss -tulpn | head -20

echo "=== recent errors ==="
journalctl -p err -n 20 --no-pager

Why this is worth automating

  • Incident response. One command produces the same picture from every host, so you compare like with like instead of remembering nine commands under pressure.
  • Inventory. Run it across the fleet and you have an asset register that is true today rather than true in 2023.
  • Drift detection. Store the output, diff it weekly: an unexpected new listening port or a changed kernel is exactly what you want to notice.
  • Bug reports. Attach it and stop the "what version are you on?" round trip.

Two upgrades

Emit machine-readable output as well as human — lsblk -J, ip -j, lscpu -J all speak JSON, so the same script can feed both a human and a dashboard. And guard every command: command -v lscpu >/dev/null || echo "lscpu unavailable", because a minimal container has none of these.

Careful: this output includes hostnames, IPs, listening ports and process names. It is a reconnaissance report. Do not paste it into a public issue tracker unredacted.

Scenario 13

Installing a LAMP stack — the idempotence lesson

#!/usr/bin/env bash
# provision-lamp.sh — safe to run twice. That is the entire point.
set -euo pipefail
[[ $EUID -eq 0 ]] || { echo "run as root" >&2; exit 1; }

export DEBIAN_FRONTEND=noninteractive     # never block on a dialogue box

apt-get update -qq
apt-get install -y --no-install-recommends \
        apache2 mariadb-server php libapache2-mod-php php-mysql

# Idempotent config: only act if the desired state is not already true
a2enmod rewrite >/dev/null                   # a2enmod is itself idempotent

if ! grep -q '^ServerTokens Prod' /etc/apache2/conf-available/security.conf; then
    sed -i 's/^ServerTokens.*/ServerTokens Prod/' /etc/apache2/conf-available/security.conf
    touch /run/apache-needs-reload
fi

# Idempotent database bootstrap — CREATE ... IF NOT EXISTS does the work
mysql --protocol=socket <<'SQL'
CREATE DATABASE IF NOT EXISTS appdb CHARACTER SET utf8mb4;
CREATE USER IF NOT EXISTS 'app'@'localhost' IDENTIFIED BY '__FROM_SECRET_STORE__';
GRANT SELECT, INSERT, UPDATE, DELETE ON appdb.* TO 'app'@'localhost';
FLUSH PRIVILEGES;
SQL

systemctl enable --now apache2 mariadb
[[ -e /run/apache-needs-reload ]] && { systemctl reload apache2; rm -f /run/apache-needs-reload; }

# Verify — provisioning is not finished until the stack answers
curl -fsS http://127.0.0.1/ >/dev/null && echo "LAMP up on $(hostname -f)"

Idempotence, concretely

Every statement above expresses desired state, not an action: install -y is a no-op if installed, IF NOT EXISTS is a no-op if present, enable --now is a no-op if running, and the sed is guarded by a grep. So a run that dies halfway can simply be re-run — which is the property that makes unattended provisioning survivable.

What is still wrong with it

  • The password. It must come from a secret store or an environment injected at run time — never a literal, and never in Git.
  • No versions pinned. The same script gives you different software next month.
  • No mysql_secure_installation equivalent, no firewall, no TLS. This is a lab stack, not a production one.
  • Only reload when something changed — the flag file above is the hand-rolled version of a configuration-management "handler".

Where this goes next

Ansible, Puppet, Chef and Salt exist because everyone writes this script and then discovers they need ordering, handlers, dry-run, host inventories and reporting. An Ansible playbook is this file with the idempotence guaranteed by the tool instead of by your grep. Write it by hand once — then you will understand what state: present is actually doing, and why a container image is usually a better answer than provisioning a mutable server at all.

Scenario 14

Get the NIC's IP address — a small task with sharp edges

The fragile answers

ifconfig | grep 'inet ' | awk '{print $2}'
# ifconfig is deprecated and absent on modern minimal installs;
# its output format differs across distributions and locales.

hostname -I
# Returns ALL addresses, space separated, in NO defined order:
#   "10.0.2.15 172.17.0.1 192.168.49.1 fd00::1"
# Fine interactively. In a script it silently picks docker0 one day.

ip addr | grep inet | head -1
# Returns 127.0.0.1. Congratulations, you have found the loopback.

All three appear in student scripts, and all three work perfectly on the laptop where they were written.

The answers that hold up

# 1. The IP on the interface used to reach a given destination —
#    usually the question you actually meant. No packets are sent.
ip -4 route get 8.8.8.8 | awk '{print $7; exit}'

# 2. A named interface, parsed as JSON instead of as text
ip -j -4 addr show dev eth0 |
    jq -r '.[0].addr_info[0].local'

# 3. The default-route interface, then its address
IFACE=$(ip -j route show default | jq -r '.[0].dev')
ip -j -4 addr show dev "$IFACE" | jq -r '.[0].addr_info[0].local'

# 4. The PUBLIC address, when behind NAT — a different question entirely
curl -fsS --max-time 5 https://api.ipify.org

Ask which IP you actually want before writing the command: the private address on a specific NIC? whichever address reaches the internet? the public address after NAT? the address other services should connect to? These are four different values, and on a cloud host with Docker, a VPN and IPv6 they are four different answers. The general lesson beyond IP addresses: prefer machine-readable output (ip -j, lsblk -J) over parsing text formatted for humans — human formats change between versions and locales, and your awk '{print $2}' silently starts returning the wrong column.

The point of Unit 2

Scenarios where automation prevents errors

Errors it genuinely removes

  • Omission. Multi-step procedures where step 7 of 12 is skipped under pressure — the single largest category. A script cannot forget.
  • Transcription. Mistyped hostnames, IPs, table names; the right command on the wrong server. This is where the famous outages come from.
  • Drift. Servers that were configured identically in March and are not identical now, because three people made small manual fixes.
  • Fatigue errors. Anything performed at 3 a.m., during an incident, or for the fortieth time in a row.
  • Rare-procedure errors. Failover, restore, certificate renewal — done twice a year, therefore done badly. Automation makes rehearsal cheap, and rehearsal is what makes it work on the day.
  • Ordering and timing errors. Migrate before deploy, drain before restart, backup before upgrade.
  • Cleanup omissions. The temp file, the debug flag, the firewall rule "opened for five minutes" in 2024.

Errors it creates, and how to contain them

  • Scaled mistakes. A wrong manual command breaks one server; a wrong script breaks five hundred, in nine seconds. Contain with: staged rollout, canary hosts, a --limit flag.
  • Silent failure. The job has failed nightly for a month and nobody knows. Contain with: alert on absence of success, non-zero exit codes, dead-man's switches.
  • Stale assumptions. The script encodes a truth from two years ago. Contain with: assertions that check preconditions and abort loudly.
  • Automation complacency. Nobody remembers how to do it by hand, and nobody reads the output any more. Contain with: game days, manual drills, rotating ownership.
  • Unreviewed power. A script with production credentials that anyone can edit. Contain with: code review, version control, least privilege.

Automation does not remove errors. It moves them from execution time to authoring time — where they are cheap, reviewable, and testable before they touch a server.

Unit 2 gave you fourteen scenarios and about six ideas

  1. Verify, do not assume. gzip -t, curl --fail, sha256sum -c, a health check after deploy.
  2. Be idempotent. Express desired state so a re-run is always safe.
  3. Validate at the boundary. Allow-list input, quote every expansion, canonicalise paths.
  4. Be reversible. Trash, do not delete; refuse to overwrite; keep a way back.
  5. Alert on the absence of success, and alert on changes of state, not on state.
  6. Never let a secret touch a command line, a repository or a log.
