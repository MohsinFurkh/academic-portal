Reveal · the question picks the model

Each question needs a different abstraction of the same junction

Question Model family What you represent What you throw away
Q1 Never both green? Automaton — states and transitions Signal states, controller transitions, sensor inputs Time, traffic volume, geography, everything continuous
Q2 No lane starves? Logic — temporal properties over runs “Always”, “eventually”, “until” over infinite executions How long “eventually” takes — logic gives order, not duration
Q3 Average wait? Queueing — arrivals and service Arrival rate, service rate, queue discipline, distributions The controller's exact logic; correctness entirely
Q4 Knock-on congestion? Graph — network structure Junctions as vertices, roads as edges, flow as weights What happens inside any single junction

The sentence the hour turns on: a model is not a simplified copy of the system — it is a deliberate deletion of everything the question does not need.

Which means there is no such thing as “the model of the junction”, and asking which model is most accurate is the wrong question. Ask which deletions are safe for the question you are asking.

Part A · the role of models

Why build a model rather than just run the system?

What a model gives you that a system cannot

  • Reasoning over all cases. A model has finitely describable structure, so you can prove things about infinitely many executions. This is the II.5 link — proof needs a model to be about.
  • Analysis before construction. You can evaluate a design that does not exist yet, for the cost of thinking.
  • Explanation, not just measurement. A benchmark tells you the system slowed down; a queueing model tells you why, and what would fix it.
  • Prediction outside the measured range. Extrapolating a benchmark is guessing; extrapolating a validated model is reasoning.
  • A shared vocabulary. “It is a DAG”, “it is an M/M/1 queue”, “it is a lattice” imports decades of results for free.

The four things every model does to reality

  1. Abstraction — deletes detail deemed irrelevant. The traffic automaton has no notion of a car.
  2. Idealisation — assumes convenient properties reality lacks. Instantaneous messages, infinite memory, Poisson arrivals.
  3. Formalisation — fixes a precise notation so claims become checkable. This is what turns an opinion into a theorem.
  4. Parameterisation — exposes the few quantities you will vary. λ, μ, n, k — the knobs the analysis turns.

Every one of those four is where a model can betray you, and step 2 most of all. Idealisations are chosen for tractability, not for truth — and a result that depends on an idealisation reality violates is the classic failure named in Unit I.

Part B · families 1 and 2

Automata: behaviour over time · Logic: properties of that behaviour

Automata-based models

Core idea: a system is a set of states and transitions between them, driven by inputs or events.

Variants: finite automata (DFA/NFA) · pushdown automata · Turing machines · labelled transition systems · Petri nets (concurrency, resources) · timed automata (real-time) · statecharts (hierarchical, used in UML).

Answers: Is this state reachable? Can the system deadlock? Does the protocol accept exactly this language? What is the minimal machine recognising this behaviour?

CS use: lexers and parsers, protocol specification, controller design, model checking, regex engines, workflow verification.

Deletes: data values (usually), continuous time, performance, and anything about how long.

Signature limit: state explosion — n components with k states each give kⁿ states. This is the single reason model checking does not scale for free.

Logic-based models

Core idea: express what must be true, in a formal language with rules of inference — then derive or check consequences.

Variants: propositional and first-order logic · temporal logic (LTL, CTL — “always”, “eventually”, “until”) · Hoare logic (pre/postconditions) · separation logic (heaps and pointers) · description logics (ontologies) · type theory.

Answers: Does this property hold on every execution? Is the specification consistent? Does the program meet its contract? Is this entailed by what we assumed?

CS use: program verification, specification languages, SAT/SMT solving, knowledge representation, static analysis, type systems.

Deletes: quantity, cost, probability, and duration — logic tells you whether and in what order, never how much or how fast.

Signature limit: the specification problem — writing the property correctly is often harder than checking it, and a verified system meeting the wrong spec is still wrong.

These two are natural partners: the automaton supplies the behaviour, the logic states the property, and a model checker searches the first for violations of the second.

Part B · families 3 and 4

Graphs: structure and relation · Algebra: composition and laws

Graph-based models

Core idea: represent entities as vertices and relationships as edges, then use structural properties to answer questions.

Variants: directed and undirected · weighted · DAGs · trees · bipartite · hypergraphs · multilayer and temporal (evolving) graphs · probabilistic graphical models (Bayesian networks, Markov random fields).

Answers: What is connected to what? What is the shortest or cheapest path? Which nodes are critical? Is there a cycle? What is the community structure? How does something spread?

CS use: networks and routing, dependency resolution, call graphs and control-flow graphs, scheduling, social-network analysis, knowledge graphs, GNNs, task DAGs.

Deletes: everything inside a vertex, and any relationship that is not pairwise. If your real relation involves three parties at once, a plain graph has already lied to you.

Signature limit: the modelling choice is doing the work — the same system gives completely different answers depending on what you decided a vertex is.

Algebraic models

Core idea: a set of objects with operations that combine them, obeying stated laws — reason by equation and substitution.

Variants: monoids and groups · lattices (used in static analysis) · Boolean and relational algebra · process algebras (CCS, CSP, π-calculus) · λ-calculus · category-theoretic models · algebraic data types and specifications.

Answers: Are these two systems equivalent? Can this be safely decomposed and recombined? Does this optimisation preserve meaning? Does the computation converge to a fixed point?

CS use: relational databases and query optimisation, compiler transformations, concurrency semantics, MapReduce (associativity!), CRDTs, functional programming, abstract interpretation.

Deletes: the concrete representation entirely, and usually all cost — algebra says two expressions are equal, never which is cheaper.

The distinctive payoff: algebraic laws license you to rewrite a system and know you have not changed its meaning. Every query optimiser and every compiler pass rests on this.

Part C · when the question is “how much?”

The four families answer whether. These answer how much.

Probabilistic models

Markov chains (states with transition probabilities) · Markov decision processes · Bayesian networks · stochastic processes.

Answers: long-run probability of being in a state; expected time to failure; how belief updates on evidence.

CS use: reliability and availability, randomised algorithms, PageRank, cache-hit modelling, fault tolerance.

Watch: the Markov assumption — the future depends only on the present state. Real systems have memory.

Queueing models

Arrivals meet a server. Kendall notation A/S/c — M/M/1, M/M/c, M/G/1 — with arrival rate λ and service rate μ.

Answers: expected queue length, waiting time, utilisation, and where the bottleneck is.

Two results worth knowing: Little's Law (L = λW — average number in system = arrival rate × average time in system, and it holds almost regardless of the distributions) and the fact that waiting time explodes as utilisation approaches 1, which is why running a server at 95% load feels catastrophic rather than efficient.

Watch: Poisson arrivals are assumed for tractability; real traffic is bursty and correlated.

Simulation models

Discrete-event, Monte Carlo, agent-based. Execute the model rather than solving it.

Answers: anything the analytic models are too complex to solve in closed form.

CS use: network simulators (ns-3), datacentre and scheduler simulation, cache and architecture simulators.

Watch — and this is important: simulation output is data, so it inherits every obligation from II.4. Multiple seeds, confidence intervals, warm-up discarded. A simulation is an experiment on a model, not a proof.

These are the models Lecture II.7 runs on: performance evaluation is largely the business of choosing one of these and defending its assumptions.

Part C · model validation

A model is a claim. It has to be defended like one.

Five ways to validate a model

  1. Face validity. Do domain experts agree the structure reflects the system? Cheap, weak, and still worth doing.
  2. Assumption audit. List every assumption and mark it plausible, questionable or known false but convenient. Publish the list.
  3. Extreme-case checking. Set parameters to limits where you know the answer. λ → 0 should give zero wait; utilisation → 1 should blow up. If it does not, the model is wrong.
  4. Empirical calibration. Fit parameters on one dataset, then check predictions against a held-out one. The II.4 discipline applies.
  5. Sensitivity analysis. Vary each assumption and see whether the conclusion survives. The single most valuable and most skipped step.

Item 5 is the one to do: if your conclusion flips when an assumption moves 10%, the conclusion is about the assumption, not about the system.

Four ways models fail in student work

  • Over-abstraction. Deleted the thing that mattered. A queueing model of a service whose real problem is a lock, not a queue.
  • Over-fitting the model to the system. So many parameters it reproduces the measurements and predicts nothing. A model with a knob per observation has explained nothing.
  • Unvalidated adoption. Using M/M/1 because it was in the textbook, never checking whether arrivals are anything like Poisson.
  • Model–system substitution. Proving a property of the model and reporting it as a property of the system, with no bridge stated between them.

The honest sentence that repairs the last one, and belongs in your report: “This result holds for the model described in §3. It transfers to the implementation to the extent that assumptions A1–A4 hold, of which A3 is the weakest.”

Do · 9 minutes · the piece of work you keep

Choose a model for your own system — and audit what it deletes

1 · 4 min alone — pick the family, list the deletions 2 · 3 min swap — neighbour attacks one deletion 3 · 2 min — decide: defend it, or change model 9:00

Step 1 · Six lines

  1. The question your model must answer — one sentence, from your Section 5 claim.
  2. Family — automata · logic · graph · algebraic · probabilistic/queueing · simulation.
  3. Entities — what is a state, a vertex, an object, a customer? This choice does most of the work. State it precisely.
  4. Parameters — the quantities you will vary.
  5. Deletions — five things about the real system your model does not represent.
  6. The dangerous one — which single deletion could change your answer, and why you are accepting it anyway.

If your project has no formal model — many will not — do this for the implicit one you are already using. A benchmark assumes a workload model. A test set assumes a distribution. An accuracy figure assumes a cost model in which every error costs the same. Name it; that is your model.

Step 2 · Rules for the attacker

Pick one deletion from their list and make the case that it matters. Use this form:

“Your model deletes ______. But in the real system, ______ — so your answer would change if ______.”

Then the owner must choose, out loud, one of exactly three responses:

  • “It does not matter, because…” — a defence, and it goes in the paper.
  • “It matters — I need a different model.” — better found today than in November.
  • “It matters and I accept it as a limitation.” — legitimate, if written down.

All three are good answers. Only silence is a bad answer — and silence is what an unexamined model produces.

Consolidation

Eight things that must survive this hour

  1. A model is a deliberate deletion of everything the question does not need — not a simplified copy.
  2. There is no “the model” of a system. The question picks the model.
  3. Automata = behaviour over states and transitions. Limit: state explosion.
  4. Logic = what must be true, and in what order. Limit: writing the spec correctly.
  1. Graphs = entities and pairwise relations. Limit: the choice of what a vertex is.
  2. Algebra = objects, operations and laws — and laws let you rewrite safely.
  3. Every model does four things: abstract · idealise · formalise · parameterise, and idealisation is where it betrays you.
  4. Sensitivity analysis is the validation step that matters. A simulation is an experiment on a model, not a proof.

If you remember one sentence: state what your model deletes, and state which deletion would change your answer — a model whose assumptions are listed can be argued with, and one whose assumptions are hidden can only be believed or dismissed.
